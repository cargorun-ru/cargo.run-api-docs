# Аудит документации CARGO.RUN Логистика

Дата проверки: 2026-10-12
Область: `docs/products/cargorun-logistics/**`

## Итог

Документация описывает основные сценарии и после проверки согласована с актуальным
внутренним Swagger и реализацией API. Уточнены правила идентификации заявки,
перезаписи через `Apply`, порожних заявок и асинхронной синхронизации API 2.0.
Оставшиеся вопросы относятся в основном к полноте публичного контракта, переходам
статусов, единицам измерения и квотам.

Внутренний Swagger использован только для проверки и не публикуется клиентам.
Раздел для LLM и ИИ-агентов, машиночитаемые файлы и Skill добавлены в публичную
документацию.

## Требуют решения владельца API

| Приоритет | Проблема | Почему это неоднозначно | Что зафиксировать |
|---|---|---|---|
| P0 | Форматы времени описаны не для всех моделей | Для ключевых полей правило уточнено по коду, но во многих API-моделях одновременно существуют локальные `DateTime` и поля `DateTimeOffset` | Для каждого оставшегося поля: UTC/локальное время, допустимые ISO 8601 варианты, точность и трактовка отсутствующей зоны |
| P1 | Нет публичной OpenAPI-схемы | Клиенты не могут автоматически сверить модели и примеры с фактическим контрактом | Поддерживать таблицы публичной документации как отдельный контракт и проверять их в CI по внутренней схеме |
| P1 | Нет таблицы переходов статусов | Перечень `BidStatus` есть, но допустимые переходы и предусловия действий не определены | State machine: исходный статус, действие, новый статус, ошибки |
| P1 | Базовый URL описан по-разному | Указаны `app.cargorun.ru/api/`, `api.app.cargorun.ru`, `api.test...` и клиентский домен | Один шаблон `<baseUrl>`, список сред и правило добавления `/api` |
| P1 | Версионирование заявлено, но не видно в URL | Введение говорит, что версия отражается в URL, однако все пути имеют вид `/api/...` | Текущую версию, политику совместимости и способ выбора версии |
| P1 | Формат ошибок зависит от метода | Упоминаются plain text и `ValidationApiResult`, но не определено, где какой формат и какие коды ошибок возможны | Единую error model или таблицу ответов для каждого метода |
| P1 | `typeOptions` описан неодинаково | API называет `id` ID элемента, а пример для 1С поясняет его как идентификатор справочника | Точную семантику `id` и `entityOptionId` с одним проверенным примером разрешения значения |
| P2 | Квоты не измеримы | Упомянуты rate limit и блокировка, но нет чисел и заголовков | Лимиты, окно, `Retry-After`, заголовки квоты и длительность блокировки |
| P2 | Единицы измерения отсутствуют | У веса, объёма, длины, радиуса и температуры нет единиц и диапазонов | Единицу, точность, минимум/максимум для каждого числового поля |
| P2 | Координаты описаны двумя способами | Общий раздел показывает `latitude/longitude`, модели — GeoJSON-массив `[longitude, latitude]` | Канонический формат по каждому методу и запрет перестановки осей |
| P2 | Ответы изменяющих методов не описаны | Неясно, где получить созданный `id`, `updatedAt` и итоговый статус | HTTP-код, заголовки и модель ответа каждого POST-метода |

## Исправлено в исходниках

- унифицировано имя `cargoOwnerDictionaryItemId` в сценарии создания заявки;
- `price` в примере приведён к числовому JSON-типу;
- локальные плановые даты в примере приведены к ISO 8601 без ложного признака UTC;
- запуск заявки использует возвращённый ID, а не `0`;
- `http` и жёстко заданный production-хост заменены на `<baseUrl>`;
- унифицирован признак `isEmptyMileageBid`;
- согласовано описание двух фактически упомянутых форматов ошибок;
- завершены оборванные разделы обновления заявки и обработки ошибок;
- добавлены страница для ИИ-агентов, краткий индекс, полный машиночитаемый файл и генератор;
- статус отмены исправлен на фактическое enum-значение `Canceled`, добавлены числовые коды и правило системного статуса `Planned`;
- описана основная модель ответа авторизации;
- разграничены UTC, значения со смещением и локальные плановые даты;
- завершены четыре сценария разрешения изменений между 1С и CARGO.RUN;
- зафиксировано, что `externalId` не уникален, а последующие операции выполняются по
  `id` CARGO.RUN;
- зафиксирована полная перезапись заявки при каждом вызове `Apply`;
- для порожней заявки описаны обязательные технические заполнители и их игнорирование
  бизнес-логикой;
- описана очередь API 2.0: настройка внешней системы, задания, подтверждения версий,
  идемпотентность, повторы, callback и защита от эха;
- зафиксированы намеренное часовое окно API 2.0, объединение изменений и отсутствие
  гарантии доставки каждой смены статуса и удаления;
- добавлен гибридный алгоритм: API 2.0 для оперативного обмена и
  `GetListForExternal` для первичной загрузки и контрольной сверки.

## Критерии готовности документации

Документацию можно считать однозначной, когда:

1. каждый публичный метод имеет request/response schema и перечень HTTP-ответов;
2. все примеры проходят валидацию по опубликованной OpenAPI-схеме;
3. алгоритм синхронизации доказуемо не теряет записи при одинаковом `updatedAt`;
4. жизненный цикл заявки задан таблицей переходов;
5. один и тот же термин, тип и поле имеют одинаковую семантику во всех разделах;
6. проверка ссылок, Markdown и генерация LLM-файлов выполняются в CI.
