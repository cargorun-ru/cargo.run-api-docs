# Введение

Этот документ описывает правила интеграции с системой **CARGO.RUN Логистика** через REST API.
API предназначен для обмена данными между CARGO.RUN и внешними учётными системами (1С, ERP, WMS, мобильными приложениями, внешними сервисами и т.д.).

Документация разделена на три большие части:

1. общие правила и форматы данных;
2. сценарии интеграции;
3. API Reference (справочник методов).

---

## 1. Назначение API CARGO.RUN

API предоставляет доступ к данным и функциям системы:

- создание и редактирование заявок и заказов,
- работа с маршрутами,
- синхронизация справочников (контрагенты, водители, техника, организации),
- управление статусами заявок, титулов и ЭТРН,
- получение событий и информации о ходе перевозок,
- работа с данными сотрудников, трекеров и мобильных клиентов.

API предназначено для систем:

- 1С и её конфигураций,
- собственных ERP клиентов,
- CRM,
- внешних логистических платформ,
- сервисов телематики,
- приложений мобильных водителей,
- корпоративных интеграционных решений.

---

## 2. Архитектура интеграции

Архитектурно API CARGO.RUN устроено как REST API:

- обмен данными осуществляется по HTTPS;
- запросы и ответы передаются в формате JSON UTF-8;
- каждый метод соответствует ресурсу или действию;
- авторизация выполняется через токен.

REST-подход обеспечивает простоту интеграции, предсказуемость и совместимость с клиентскими библиотеками.

---

## 3. Версионирование

API стремится сохранять обратную совместимость. Обновления вносятся в соответствии с принципами:

- новые поля добавляются без нарушения обратной совместимости;
- изменение обязательности полей всегда оговаривается заранее;
- разрушительные изменения должны сопровождаться новой версией API и планом миграции.

Текущие методы используют пути без номера версии (`/api/...`). Поэтому перед
обновлением интеграции проверяйте журнал изменений и согласовывайте разрушительные
изменения с владельцем API.

---

## 4. Базовый URL API

Фактический адрес среды предоставляется при подключении интеграции. В документации
он обозначается как `<baseUrl>` и **не включает** суффикс `/api`.

Примеры формирования URL:

- `GET <baseUrl>/api/bids/GetListForExternal`
- `POST <baseUrl>/api/TruckingBids/Apply`
- `POST <baseUrl>/api/tasks/queue`

---

## 5. Формат запросов и ответов

- Все запросы — JSON.
- Успешные ответы обычно передаются в JSON. Ошибки отдельных методов могут быть
  JSON-объектом или обычным текстом; это указано в описании форматов.
- Кодировка — UTF-8.
- При необходимости передавать вложенные структуры используются стандартные JSON-объекты и массивы.

Во всех примерах документации используется форматирование, совместимое с JSONLint.

---

## 6. Авторизация

Доступ к API выполняется через выдачу токена.
В интеграции используется схема: Authorization: Bearer

Токен выдаётся методом авторизации и имеет срок действия.
Обновление токена (refresh) выполняется через соответствующий метод API.

Все методы, взаимодействующие с данными клиента, требуют авторизации.

---

## 7. Ограничения и квоты

API может вводить ограничения:

- лимиты на количество запросов в единицу времени (rate limit),
- ограничения на размер запросов,
- требования к обязательным полям,
- набор допустимых статусов и переходов для сущностей.

Эти ограничения фиксируются по мере необходимости в описаниях методов.

---

## 8. Следующие шаги

Для дальнейшей работы рекомендуется:

5. Для оперативного обмена изменениями заявок изучить:
   [Синхронизация заявок API 2.0](./integration/async-sync-v2.md)

# Минимальные требования к данным

Этот раздел содержит минимальные обязательные поля, которые необходимы при создании сущностей через API **CARGO.RUN Логистика**.
Значения обязательных полей должны присутствовать в запросах, иначе метод вернёт ошибку валидации.

Если метод требует дополнительные поля, они указаны в описании соответствующего метода в API Reference.

---

# 1. Создание заявки (Bid)

Минимальный набор полей зависит от того, создаётся ли заявка полностью в CARGO.RUN или поступает из внешней системы (1С, ERP).

| Поле | Тип | Описание |
|------|------|----------|
| `cargoOwnerDictionaryItemId` | number | Идентификатор заказчика (контрагента). |
| `paymentTypeId` | number | Тип оплаты. |
| `ndsTypeId` | number | Тип НДС. |
| `price` | number | стоимость в рублях (с НДС). |
| `driver` | object | Идентификатор водителя. |
| `carOption` | object | Идентификатор автомобиля (тягача). |
| `trailerOption` | object | Идентификатор полуприцепа. |
| `bidPoints` | array | Маршрутные точки (минимум две: погрузка и выгрузка). |

Для порожней заявки передайте `isEmptyMileageBid = true`. Текущая валидация также
требует технические заполнители, хотя при обработке порожней заявки их значения
игнорируются:

- `price`: например, `1`;
- `cargos`: непустой массив, например `[ { "id": 0, "name": null } ]`;
- `paymentTypeId` и `ndsTypeId`: существующие ID из справочников целевой организации.

Не придумывайте ID типов оплаты и НДС: получите допустимые значения до запуска
интеграции. `cargoOwnerDictionaryItemId` для порожней заявки можно не передавать.
Если в организации включён учёт причин порожнего пробега, объект `emptyMileageBid`
обязателен.

# 2. Создание заказа (DistributionBid)

---

# 5. Создание автомобиля (Car)

| Поле | Тип | Описание |
|------|------|----------|
| `number` | string | Госномер. |

---

# 6. Создание прицепа (Trailer)

| Поле | Тип | Описание |
|------|------|----------|
| `number` | string | Госномер. |

---

# 7. Общие правила

1. Все числовые идентификаторы (`xxxId`) должны существовать в справочниках.
2. Поля, указанные как обязательные, не могут быть `null`.
3. Любые дополнительные поля передавайте только если они описаны в соответствующем разделе API Reference.
4. Если описание конкретного метода требует больший набор полей, используйте требования этого метода.

---

# 8. Что делать при ошибке валидации

Если обязательное поле опущено или не соответствует типу:

- сервер возвращает ошибку `400 Bad Request`,
- тело ответа может быть обычным текстом или объектом `ValidationApiResult` с полем `errorMessage`; клиент должен уметь сохранить оба варианта.

Рекомендуется логировать ошибки на стороне внешней системы.

# Форматы данных

В этом разделе приведены единые форматы данных, используемые во всех методах API **CARGO.RUN Логистика**.

---

## 1. Формат даты и времени

### Основной формат

API использует ISO 8601, но трактовка часового пояса зависит от поля.

| Категория | Формат | Трактовка |
|---|---|---|
| Технические метки (`createdAt`, `updatedAt`) и границы OData-фильтров | `YYYY-MM-DDTHH:mm:ssZ` | UTC |
| Поля с суффиксом `Offset` | `YYYY-MM-DDTHH:mm:ss±HH:mm` | Момент времени с явным смещением |
| `bidPoints[].planEnterDate` и другие явно локальные плановые даты | `YYYY-MM-DDTHH:mm:ss` | Локальное время адреса точки; зона определяется по геоданным точки |

Примеры:
- `2025-03-12T15:20:00Z`
- `2025-03-12T18:20:00+03:00`
- `2025-03-12T18:20:00`

Исключение: метод получения пробегов `/api/car/getcarmileageforperiod`

В нем используется формат без часового пояса: `YYYY-MM-DDTHH:mm:ss`

Пример: `/api/car/getcarmileageforperiod?carid=694385&start=2025-10-31T21:00:00&end=2025-11-17T20:59:59`

### Особенности

- Для `updatedAt` и других технических меток используйте UTC с `Z`.
- Для `planEnterDate` передавайте локальное время точки без `Z`; геозона должна
  позволять системе определить часовой пояс.
- Не добавляйте `Z` к локальной дате: это изменит смысл времени.
- Если конкретный метод задаёт другой формат, его описание имеет приоритет.
- Доли секунды не используйте, если они не показаны в описании метода.

---

## 2. Числовые идентификаторы (ID)

Идентификаторы сущностей передаются **только как целые числа**.

Правильно:

`12345`

Неправильно:

`"12345"`

Это требование распространяется на:

- заявки (`bidId`)
- заказы (`orderId`)
- контрагентов (`counterpartyId`)
- водителей (`driverId`)
- автомобили (`carId`)
- прицепы (`trailerId`)
- организации (`organizationId`)
- сотрудников (`employeeId`)
- трекеры (`trackerId`)

---

## 3. Телефонные номера

Телефон передаётся в международном формате:

`+7XXXXXXXXXX`

Где:

- нет пробелов,
- нет дефисов,
- код страны обязательно `+7`.

Пример:

`+79991234567`

---

## 4. Координаты

Координаты передаются в виде двух числовых значений:

- **latitude** — широта
- **longitude** — долгота

Формат:

```json
{
  "latitude": 55.7558,
  "longitude": 37.6176
}
```

Допускается использование вложенных структур (например, GeoJSON), если это описано в конкретном методе API.

---

## 5. Адреса

Адрес всегда содержит следующие элементы (если применимо):

- строка адреса,
- город,
- регион,
- страна,
- геокоординаты,
- дополнительные комментарии.

Используемые поля зависят от конкретного эндпоинта.

---

## 6. Денежные значения и ставки

Стоимость, суммы, ставки и другие денежные поля передаются как числа с фиксированной точностью:

- только число, без строк;
- без символа валюты;
- разделитель — точка.

Примеры:

- `1000`
- `12000.5`
- `0.0`

---

## 7. Boolean (логические значения)

Используются стандартные JSON-значения:

- `true`
- `false`

Недопустимо:

- `"true"`
- `"yes"`
- `"0"`
- `"1"`

---

## 8. Строки

Строки передаются в кодировке UTF-8.
Допускается использование:

- точек,
- запятых,
- спецсимволов JSON,
- Unicode.

---

## 9. Enum-значения

Если поле принимает фиксированный набор значений (например, статус заявки или тип прицепа), то:
- значение должно быть строго равно одному из элементов перечисления;
- формат перечислений приведён в разделе "Статусы￼".

---

## 10. Списки и массивы

Если поле является массивом:

```json
[
  { ... },
  { ... }
]
```

Особенности:
- массив должен содержать однородные элементы;
- порядок элементов — значимый, если указано в описании метода.

---

## 11. Пагинация

Некоторые методы API поддерживают постраничную выборку.

Используются два механизма:

1. Классическая пагинация:
   - `page` — номер страницы (начиная с 1);
   - `pageSize` — количество элементов на странице.

2. OData-пагинация:
   - `$top` — максимальное количество записей;
   - `$skip` — количество записей, которые нужно пропустить.

Конкретный механизм для метода указан в описании эндпоинта (API Reference).
Если метод принимает `page`/`pageSize`, их значения должны быть целыми числами ≥ 1.
Если метод принимает `$top`/`$skip`, рекомендуется использовать их в духе OData:
- `$top` — ограничение выборки (например, 100);
- `$skip` — смещение (например, 0, 100, 200...).

---

## 12. Параметры OData

Ряд методов поддерживает фильтрацию и выборку данных в стиле OData.
В описаниях методов могут использоваться следующие параметры:

- `$filter` — фильтрация по условиям;
- `$select` — выбор отдельных полей;
- `$expand` — раскрытие связанных сущностей;
- `$orderBy` — сортировка;
- `$top` — ограничение числа записей;
- `$skip` — пропуск указанного числа записей;
- `$count` — запрос количества записей.

Конкретный синтаксис выражений в `$filter`, `$orderBy` и правила комбинации параметров следует смотреть в описании соответствующих методов API.

---

## 13. Ошибки API { #api-errors }

При ошибках бизнес-валидации API CARGO.RUN возвращает:
- HTTP-код 400 (`Bad Request`)
- тело ответа в виде обычного текста либо объекта `ValidationApiResult` с полем `errorMessage` — в зависимости от метода

Формат ответа:
```
400 Bad Request
<текст ошибки>
```

Пример:
```
400 Bad Request
Driver cannot be deleted because he has active bids
```

Клиенту не следует предполагать единственный `Content-Type` ошибки. Сначала проверьте
тип содержимого ответа; если получен JSON, прочитайте `errorMessage`, иначе сохраните
текст ответа целиком.

# Статусы сущностей

В этом разделе собраны статусные модели ключевых сущностей **CARGO.RUN Логистика**.

---

# 1. Статусы заявок (BidStatus)

Статус отражает текущее состояние заявки.
Заявка проходит несколько этапов — от создания до завершения или отмены.

| Статус | Код | Описание |
|---|---:|---|
| `New` | `0` | Заявка создана, находится в статусе черновика. |
| `Planned` | `5` | Запланирована к выполнению. |
| `Started` | `10` | Начата, запущена в работу. |
| `Canceled` | `20` | Заявка отменена. |
| `Done` | `30` | Заявка выполнена. |

### Примечания
- Статус `New` означает, что заявка еще не запущена логистом.
- Статус `Planned` означает, что заявку попытались запустить, но транспортное средство
  занято другой заявкой и у организации включено планирование. Этот статус назначает
  система; передавать `Planned` в `SetStatus` вручную нельзя.
- При запросе `Started` итоговый статус может оказаться `Planned`. Проверяйте ответ
  команды и повторно читайте заявку.
- Переходы между статусами контролируются бизнес-логикой системы.

---

# 2. Статусы оплаты заявки

Статусы отражают состояние расчётов по заявке со стороны заказчика.

| Статус | Описание |
|--------|----------|
| `NotPaid` | Оплата по заявке не поступила. |
| `PartiallyPaid` | Оплачена частично. |
| `Paid` | Полностью оплачена. |
| `Expired` | Истёк срок оплаты. |

---

# 3. Статусы контрагентов

Контрагенты могут иметь различный статус, определяющий возможность работы с ними в системе.

| Статус | Описание |
|--------|----------|
| `None` | Ограничения отсутствуют. |
| `Priority` | Приоритетный контрагент. |
| `Suspended` | Работа временно приостановлена. |

---

# 4. Статусы титулов (ЭТРН)

Электронная транспортная накладная (ЭТРН) включает несколько титулов и уровней подписания.
Фактические статусы могут отличаться в зависимости от провайдера ЭТРН, поэтому здесь указаны статусы `WaybillTitleStatus`, используемые в API.

| Статус | Описание |
|--------|----------|
| `ReceivedOrCreated` | Титул получен или создан системой. |
| `Accepted` | Титул принят водителем или внешней системой. |
| `Signed` | Титул подписан. |
| `Sent` | Титул передан на отправку в ЭДО. |
| `Processed` | Титул обработан провайдером ЭТРН. |
| `Declined` | Титул отклонён. |
| `Failed` | При обработке титула возникла ошибка. |

# Глоссарий

Этот раздел содержит основные термины, используемые в документации и API **CARGO.RUN Логистика**.
Определения даны в техническом и интеграционном контексте.

---

## Заявка (Bid)
Основная сущность планирования перевозки. Содержит:
- информацию о контрагенте (заказчике),
- параметры груза,
- маршрутные точки,
- сроки посещения точек,
- стоимость и условия оплаты,
- транспортное средство,
- водитель,
- полуприцеп.

Заявка является основой для формирования рейса.

---

## Заказ (DistributionBid)
Сущность планирования перевозки, аналогичная Заявке, но без указанных транспортного средства, водителя, полуприцепа.

Используется для управления нераспределёнными рейсами.

---

## Маршрутная точка (BidPoints)
Элемент маршрута, включающий:
- адрес,
- геокоординаты,
- даты,
- вид операции (погрузка, выгрузка, пересортировка).

Передаются массивом в сущности Заявка (Bid).

---

## Контрагент (Counterparty)
Юридическое лицо заказчика перевозки:

В API используются поля `counterpartyId` и связанные справочники.

---

## Организация (Organization)
Юридическое лицо перевозчика (транспортной компании).

---

## Водитель (Driver)
Сотрудник транспортной компании, закреплённый за рейсом.
Связан с мобильным приложением CARGO.RUN Driver.

---

## Машина (Car)
Транспортное средство — тягач или грузовик.
В API содержит:
- государственный номер,
- модель и марка,
- привязанный трекер.

---

## Прицеп / Полуприцеп (Trailer)
Дополнительное транспортное средство, используемое с тягачом.
В API содержит:
- государственный номер,
- модель и марка,
- тип полуприцепа (тент, изотерм, рефрижератор).

Может иметь привязанный трекер.

---

## Трекер (Tracker)
Устройство телематики, передающее координаты и технические данные.

В API используются методы привязки/отвязки трекеров.

---

## ЭТРН / Электронная транспортная накладная (Waybill)
Электронный аналог транспортной накладной, содержащий:
- сведения о грузе,
- отправителе,
- перевозчике,
- водителе,
- маршруте,
- титулы подписей.

API позволяет получать статусы ЭТРН, передавать титулы, QR-коды, электронные подписи и изменять статусы титулов.

---

## Сотрудник (Employee)
Человек, имеющий доступ в систему или связанный с операционными процессами:
- логист,
- водитель,
- администратор,
- бухгалтер.

---

## Статус (Status)
Текущее состояние сущности:
- заявки,
- оплаты,
- контрагента,
- ЭТРН.

Перечни статусов находятся в разделе "[Статусы](./statuses.md)".

---

## Идентификатор (ID)
Числовое значение, определяющее сущность в системе.
Все идентификаторы передаются как числа (не строки).

---

## Токен (Token)
Ключ авторизации в API, выдаётся методом авторизации.
Передаётся в заголовке: Authorization: Bearer

---

## Обновление данных (Sync / Synchronization)
Регулярное сравнение данных между внешней системой (1С, ERP) и CARGO.RUN:
- синхронизация справочников,
- обновление заявок,
- передача статусов.

Описано в разделе "[Синхронизация данных](./integration/sync.md)".

# Обзор интеграции

Этот документ описывает архитектуру и общие принципы интеграции между CARGO.RUN Logistics 2.0 и внешними системами (1С, ERP, WMS, CRM, внешние логистические платформы).
Он служит отправной точкой перед изучением сценариев и конкретных методов API.

---

# 1. Общая архитектура интеграции

Интеграция выполняется через REST API:

- обмен осуществляется по HTTPS;
- данные передаются в формате JSON;
- доступ — по токену авторизации;
- для выборок и фильтрации используется система query-параметров (включая OData-стиль).

Архитектура интеграции предполагает два возможных источника данных:

1. **CARGO.RUN → внешняя система**
   данные создаются в CARGO.RUN, внешняя система их получает;

2. **Внешняя система → CARGO.RUN**
   данные создаются во внешней системе и передаются в CARGO.RUN для планирования и исполнения.

Обе модели полностью поддерживаются.

---

# 2. Роль CARGO.RUN в потоке данных

CARGO.RUN выступает как:

- система планирования маршрутов и рейсов,
- система контроля исполнения перевозок,
- система мониторинга транспорта,
- хранилище заявок и статусов,
- точка сборки всех событий по перевозке.

Внешние системы (ERP, 1С, WMS) обычно отвечают за:

- учёт грузов,
- расчёты и финансы,
- ведение справочников,
- учёт заказчиков и заказов.

---

# 3. Базовые интеграционные возможности

API CARGO.RUN предоставляет возможности:

- создавать заявки (Bid) и заказы (DistributionBids);
- обновлять статусы заявок и ЭТРН;
- передавать маршрутные точки и параметры груза;
- синхронизировать справочники:
  - контрагенты,
  - водители,
  - автомобили,
  - прицепы,
  - организации;
- управлять трекерами (привязка/отвязка);
- получать данные о рейсах и событиях выполнения;
- получать статусы титулов  ЭТРН.

Для заявок используются два канала синхронизации: асинхронная очередь API 2.0
для оперативных изменений и `GetListForExternal` для первичной загрузки,
статусов, удалений и контрольной сверки. См.
[Синхронизация заявок API 2.0](./async-sync-v2.md).

---

# 4. Двусторонняя интеграция

Интеграция может быть:

## 4.1. Односторонняя
Только внешняя система отправляет данные в CARGO.RUN
Или наоборот, CARGO.RUN передаёт события во внешнюю систему.

## 4.2. Двусторонняя
Обе системы создают данные, обновляют статусы и синхронизируют справочники.

Типовой пример двусторонней интеграции:

- 1С создаёт заявку;
- заявка передаётся в CARGO.RUN;
- CARGO.RUN планирует и исполняет рейс;
- статусы и результаты выполнения возвращаются в 1С.

---

# 5. Основные потоки данных

Интеграция покрывает три больших направления:

## 5.1. Справочники
Передаются регулярно или по событию:

- контрагенты,
- водители,
- автомобили,
- прицепы,
- организации.

Справочники должны быть синхронизированы до создания заявок.

---

## 5.2. Документы (заявки и заказы)
Потоки данных:

1. Внешняя система создаёт заявку/заказ → отправка в CARGO.RUN.
2. CARGO.RUN создаёт заявку → внешняя система получает её через API.
3. Обновление заявок обеими сторонами.
4. Отслеживание статусов заявок.

---

## 5.3. События перевозки
CARGO.RUN может передавать или предоставлять:

- время прибытия/отъезда,
- времена начала/завершения погрузки/выгрузки,
- пробег,
- задержки,
- отклонения от маршрута.

Эти данные используются внешними системами для:

- аналитики,
- расчётов,
- контроля SLA,
- контроля выполнения перевозок.

---

# 6. Потоки статусов

Статусы меняются:

- со стороны логиста,
- со стороны ЭТРН-провайдера,
- со стороны исполнителя (водитель),
- автоматически (например, при успешном закрытии рейса).

Внешние системы могут:

- получать статусы через API,
- сверять статусы заявок,
- сохранять историю изменений у себя.

---

# 7. Требования к идентификаторам

Для корректной интеграции обязательны:

- единые ID справочников;
- фиксированные значения статусных моделей;
- строгое соответствие названий полей, указанным в API Reference.

Дубликаты или ошибки в идентификаторах приводят к конфликтам в данных.

---

# 8. Принципы синхронизации данных

- Данные синхронизируются по методу «запрос → ответ».
- Для выборок поддерживаются фильтры и пагинация.
- Для оптимизации могут использоваться:
  - `updatedAt`,
  - `$filter` c условиями,
  - `$top` / `$skip`,
  - `$orderby`.

Синхронизация справочников и заявок описана в посвящённом разделе.

# Сценарий: заявка создаётся в CARGO.RUN

Этот сценарий описывает ситуацию, когда заявка (Bid) создаётся и редактируется в системе CARGO.RUN, а внешняя система (1С, ERP или другое приложение) должна получать эти данные, реагировать на изменения и использовать их в собственных процессах.

---

# 1. Структура процесса

Процесс синхронизации в этом сценарии включает три части:

1. **CARGO.RUN создаёт и изменяет заявки.**
2. **Внешняя система получает новые или обновлённые заявки через API 2.0 и выполняет контрольную сверку.**
3. **Внешняя система сохраняет данные и обновляет статусы у себя.**

Внешняя система не должна создавать заявку в CARGO.RUN — только принимать и обрабатывать.

---

# 2. Создание заявки в CARGO.RUN

Заявки формируются логистами CARGO.RUN:

- выбор контрагента,
- указание маршрута и точек,
- выбор водителя и автомобиля,
- назначение стоимости и НДС,
- уточнение условий перевозки.

После сохранения заявка получает статус `New` или `Planned`, в зависимости от процесса клиента.

---

# 3. Получение заявок внешней системой

Внешняя система должна периодически выполнять запрос на получение заявок, созданных или обновлённых после определенного момента времени.

Типовой алгоритм:

1. Хранить границу последнего полностью обработанного окна синхронизации.
2. Для оперативных изменений использовать `POST/GET /api/tasks/queue` и
   `ReadConfirmation`; вызывать чтение чаще одного раза в час.
3. Зафиксировать новую верхнюю границу и выполнить первичную или контрольную выборку
   методом `GET /api/bids/GetListForExternal`.
4. Получать фиксированное окно порциями по 50 записей через `$top=50` и `$skip`.
5. Сортировать результат по `updatedAt,id` и идемпотентно сохранять по `id` и `updatedAt`.
6. Учитывать `isDeleted = true`, а не отбрасывать удалённые заявки.
7. Продвигать границу только после успешной обработки всех страниц; следующее окно
   начинать с перекрытием для защиты от совпадающих меток времени.

Пример запроса:

```http
GET /api/bids/GetListForExternal
  ?$filter=updatedAt ge 2024-01-23T21:00:00Z
           and updatedAt le 2024-01-25T20:59:59Z
           and createdAt ge 2022-09-30T21:00:00Z
  &$top=50
  &$orderby=updatedAt,id
  &$skip=0
```

Подробный алгоритм приведён в разделах [Синхронизация данных](./sync.md) и
[Синхронизация заявок API 2.0](./async-sync-v2.md).

---

# 4. Синхронизация справочников перед обработкой заявок

Перед обработкой новых заявок внешняя система должна обеспечить актуальность справочников:

- контрагенты,
- водители,
- автомобили,
- прицепы,
- организации.

Если у заявки указан водитель с `driverId`, который отсутствует в внешней базе, система должна либо:

- предварительно загрузить справочник водителей,
- либо запросить данные этого водителя.

---

# 5. Обработка статусов заявок

CARGO.RUN управляет статусами заявки (этапы выполнения рейса).
Внешняя система должна регулярно получать актуальные статусы через
`GET /api/bids/GetListForExternal`. API 2.0 пока не гарантирует доставку каждой смены
статуса и удаления, поэтому очередь не заменяет контрольную выборку.

Статусы, которые важно отслеживать:

- `Planned`
- `New`
- `Done`
- `Canceled`

Внешняя система должна обновлять свои записи в соответствии с полученными статусами.

---

# 6. Обработка событий перевозки

Дополнительно могут передаваться:

- фактические времена прибытия,
- времена начала/завершения погрузки/выгрузки,
- пробег,
- задержки,
- отклонения от маршрута.

Эти данные используются во внешних системах для:

- расчёта KPI,
- учёта времени,
- проверки SLA,
- расчётов с перевозчиком.

---

# 7. Частота синхронизации

Подходы:

- **периодически** — каждые 1–5 минут (рекомендуемый вариант),
- **по расписанию** — например, каждые 15 минут,
- **только вручную** — если система не требует оперативного обновления (не рекомендуется).

При высокой нагрузке возможно использовать:

- `$top=50`
- `$skip` для перехода к следующей странице
- `$orderby=updatedAt`
- инкрементальные загрузки.

Не запрашивайте полный список без ограничения количества записей. Для минимизации нагрузки на сервер списки нужно получать порциями по 50 записей; при тяжелых запросах пользователь может быть временно заблокирован системой.

---

# 8. Обработка ошибок и конфликтов

Внешняя система должна корректно обрабатывать:

- отсутствие данных,
- некорректные значения справочников,
- недоступность API,
- устаревшие timestamp (если синхронизация задержалась).

При ошибке желательно:

- повторить запрос,
- логировать ситуацию,
- не терять timestamp последней успешной синхронизации.

---

# 9. Что изучать дальше

  [Внешняя система → CARGO.RUN](./scenario-external-to-cr.md)

- Механизмы синхронизации:
  [Синхронизация данных](./sync.md)

- Минимальные требования к данным:
  [Минимальные требования](../minimal-requirements.md)

# Сценарий: заявка создаётся во внешней системе

Этот сценарий описывает процесс, в котором внешняя система (1С, ERP, WMS или другая учетная система) является источником создания заявок.
CARGO.RUN принимает данные, формирует рейсы, управляет маршрутом, контролирует исполнение и возвращает статусы во внешнюю систему.

---

## 1. Общая последовательность процесса

Процесс включает следующие этапы:

1. Внешняя система формирует заявку или заказ.
2. Перед отправкой заявка проходит проверку данных.
3. Внешняя система отправляет заявку в CARGO.RUN.
4. CARGO.RUN создаёт заявку **в статусе `New` (Черновик)**.
5. Внешняя система **запускает заявку в работу**.
6. CARGO.RUN планирует и исполняет рейс.
7. Внешняя система регулярно получает обновления статусов заявки.

---

## 2. Требования к данным перед отправкой

Перед тем как создать заявку в CARGO.RUN, внешняя система должна убедиться:

- все необходимые справочники синхронизированы:
  - контрагенты,
  - водители,
  - автомобили,
  - прицепы,
  - организации;

- обязательные поля заполнены (см. раздел "Минимальные требования"):
  - `cargoOwnerDictionaryItemId`,
  - `paymentTypeId`,
  - `ndsTypeId`,
  - `carId`,
  - `driverId`,
  - `bidPoints`.

- значения идентификаторов (`xxxId`) существуют в системе.

Если справочники не синхронизированы, система вернет ошибку валидации.

---

## 3. Создание заявки во внешней системе

Обычно внешняя система формирует заявку на основе внутренних процессов:

- формирование груза,
- данные клиента,
- информация по отправителю/получателю,
- планируемая дата доставки,
- параметры перевозки.

После формирования заявки данные приводятся к структуре JSON, соответствующей требованиям API CARGO.RUN.

После создания черновика необходимо запустить заявку:

```
POST /api/TruckingBids/SetStatus
```

Тело запроса:

```json
{
  "bidId": 123456,
  "status": "Started"
}
```

Здесь `123456` — `id`, возвращённый при создании заявки. Значение `0` используется
только при создании и не подходит для последующего изменения статуса.

## 6. Получение статусов и списка заявок во внешней системе

Для инкрементальной синхронизации с внешней системой используется метод:

```
GET /api/bids/GetListForExternal
```

Метод возвращает HTTP-статус `200` и массив заявок.

### Принцип работы синхронизации

У каждой заявки в CARGO.RUN есть поле:

```text
updatedAt
```

Это дата последнего обновления заявки.
В процессе синхронизации используется следующий алгоритм:

1. Внешняя система фиксирует верхнюю границу окна и запрашивает заявки, у которых
   `updatedAt` попадает в это окно.
2. Все страницы окна обрабатываются идемпотентно по `id` и `updatedAt`.
3. Верхняя граница сохраняется как новый рубеж только после успешной обработки всех страниц.
4. Следующее окно начинается с небольшим перекрытием; дубликаты допустимы и отбрасываются.

Полный алгоритм и его ограничения описаны в разделе
[Синхронизация данных](./sync.md#sync-updated-at).

### Пример запроса

```text
<baseUrl>/api/bids/GetListForExternal
  ?$filter=updatedAt ge 2024-01-23T21:00:00Z
           and updatedAt le 2024-01-25T20:59:59Z
           and createdAt ge 2022-09-30T21:00:00Z
  &$top=50
  &$orderby=updatedAt,id
  &$skip=0
```

Запрос вернёт список заявок:

- с датой обновления больше `24.01.2024 00:00` (МСК)
  (`23.01.2024 21:00:00` UTC);
- с датой обновления меньше `25.01.2024 23:59` (МСК)
  (`25.01.2024 20:59:59` UTC);
- с датой создания больше `30.09.2022` (если необходимо ограничение по дате создания);
- первые `50` заявок (параметр `$top`), начиная с `0` (`$skip=0`);
- отсортированные по полю `updatedAt`.

---

## 7. Обработка ошибок и корректировка данных

Типовые причины ошибок при создании и обновлении заявок:

- несоответствие идентификаторов справочников (водители, автомобили, прицепы, контрагенты);
- некорректные адреса и геозоны;
- некорректная структура массива `bidPoints`;
- отсутствие обязательных полей.

Рекомендуется:

- логировать все ошибки на стороне внешней системы;
- отображать текст ошибки операторам;
- повторять запрос после исправления данных.

---

## 8. Обновление заявки

Для обновления заявки поддерживаются два подхода.

### 8.1. Полное обновление заявки

Вызовите `POST /api/TruckingBids/Apply` и передайте полную актуальную модель заявки
с её `id > 0`. Каждый вызов полностью перезаписывает заявку: отсутствующие значения
могут быть потеряны или сброшены. Перед обновлением получите актуальную карточку и
объедините изменения.

### 8.2. Частичное обновление заявки

Вызовите `POST /api/TruckingBids/Patch`. Для вложенных коллекций действуют особые
правила: массив `bidPoints` передаётся целиком, даже при изменении одной точки.
Подробности и ограничения приведены в [справочнике методов заявок](../api/bids.md#bid-patch).

# Синхронизация справочников и заявок

Этот документ описывает порядок синхронизации данных между внешней системой (1С/ERP/WMS) и CARGO.RUN.
Синхронизация одинакова для обоих сценариев интеграции: когда заявка создаётся в CARGO.RUN и когда она создаётся во внешней системе.

---

## 1. Общие принципы синхронизации

Синхронизация выполняется через REST API CARGO.RUN по протоколу HTTPS с использованием токена авторизации.

Каждый объект (водитель, машина, прицеп, контрагент, организация, заявка):

- имеет уникальный идентификатор `id` в CARGO.RUN;
- при создании в CARGO.RUN возвращает этот `id`, который должен быть сохранён во внешней системе;
- содержит поле `updatedAt`, отражающее дату и время последнего изменения.

Поле `updatedAt` используется как основа для инкрементальной синхронизации.

Для заявок применяйте два взаимодополняющих канала:

- [асинхронную очередь API 2.0](./async-sync-v2.md) — для оперативного обмена;
- `GET /api/bids/GetListForExternal` — для первичной загрузки, статусов, удалений и
  контрольной сверки.

---

## 2. Справочники, подлежащие синхронизации

### 2.1. Справочники, данные которых поступают из внешней системы

Эти справочники всегда считаются первичными во внешней системе:

- Водители
- Машины
- Прицепы
- Контрагенты
- Организации

Для них внешний идентификатор является источником истины, а CARGO.RUN — получателем.

Синхронизация выполняется через методы:

- `/api/Driver/Apply`, `/api/Driver/Delete`, `/api/Driver/Restore`, `/api/Driver/GetList`
- `/api/Car/Apply`, `/api/Car/Delete`, `/api/Car/GetList`, `/api/Car/GetForEdit`
- `/api/Trailer/Apply`, `/api/Trailer/Delete`, `/api/Trailer/GetList`
- `/api/CargoOwnerDictionary/Apply`, `/api/CargoOwnerDictionary/Delete`, `/api/CargoOwnerDictionary/Get`
- `/api/LegalPersons/Apply`, `/api/LegalPersons/Delete`, `/api/LegalPersons/GetList`

**Рекомендуемая частота синхронизации: не больше чем раз в 1 минуту.**

---

### 2.2. Ограничения на удаление водителей, машин и прицепов

При удалении объектов-справочников (водителей, машин, прицепов) действуют бизнес-ограничения.

Система не позволяет удалить объект, если он используется в актуальных данных, например:

- водитель назначен на активную или запланированную заявку;
- машина участвует в активной заявке;
- прицеп привязан к активной заявке или рейсу.

В этих случаях:

- операция удаления завершается ошибкой (HTTP-статус 4xx);
- в ответе возвращается текстовое пояснение причины, например что объект используется в заявке и не может быть удалён.

Рекомендуется при интеграции:

- логировать текст ошибки;
- отображать комментарий пользователю внешней системы;
- при необходимости реализовать бизнес-процесс «вывода из эксплуатации» (деактивацию) вместо физического удаления.

---

### 2.3. Справочники, данные которых поступают из CARGO.RUN

- Тип оплаты (`PaymentType`)
- Тип НДС (`NDSType`)
- Тип груза (`CargoType`)
- Типы машин (`CarType`)
- Типы прицепов (`TrailerType`)
- Бренды машин (`CarBrandType`)
- Бренды прицепов (`TrailerBrandType`)

Получение выполняется методом:

```
GET /api/catalogs/getSimple?$filter=externalId eq null&$orderby=id desc
```

Метод поддерживает OData-фильтры.

---

## 3. Использование справочников при создании заявок

Поля, заканчивающиеся на `TypeId` (например, `paymentTypeId`, `ndsTypeId`, `typeId`, `brandTypeId`) должны заполняться значениями из общих справочников.

Некорректные идентификаторы приведут к ошибке валидации.

---

## 4. Синхронизация заявок (Bid)

Заявка — основной объект интеграции.
Синхронизация выполняется по полю:

```
updatedAt
```

Существует два направления синхронизации:

1. **Внешняя система → CARGO.RUN**
   (создание/обновление через `/api/TruckingBids/Apply` или `/api/TruckingBids/Patch`)

2. **CARGO.RUN → внешняя система**
   (оперативные изменения через `/api/tasks/queue`, первичная загрузка и сверка через
   `/api/bids/GetListForExternal`)

---

## 5. Обработка `updatedAt` { #sync-updated-at }

Не используйте максимальный `updatedAt` последней страницы как единственный курсор:
несколько заявок могут иметь одинаковую метку времени, а состав выборки меняется во
время постраничного чтения.

Рекомендуемый алгоритм:

1. До начала цикла зафиксировать верхнюю границу `windowEnd` в UTC.
2. Взять нижнюю границу `windowStart` из состояния последней **полностью успешной**
   синхронизации и отступить назад на небольшой интервал перекрытия.
3. Запросить фиксированное окно `updatedAt ge windowStart and updatedAt le windowEnd`
   с `$orderby=updatedAt,id`, `$top=50` и последовательным `$skip`.
4. Обработать все страницы; повторные записи безопасно обновлять по паре `id` и
   `updatedAt`. Учитывать записи с `isDeleted = true`.
5. Только после успешной обработки всего окна атомарно сохранить `windowEnd` как
   новый завершённый рубеж.
6. При ошибке не продвигать рубеж и повторить окно. Периодически выполнять
   контрольную сверку за более длинный период.

Перекрытие и дедупликация дают семантику «как минимум один раз», а не «ровно один
раз». Документация API пока не определяет составной серверный курсор для записей с
одинаковым `updatedAt`, поэтому обработчик должен быть идемпотентным.

---

## 6. Получение списка заявок из CARGO.RUN

Основной метод для инкрементальной синхронизации:

```
GET /api/bids/GetListForExternal
```

### Пример запроса

```
/api/bids/GetListForExternal
?$filter=updatedAt ge 2024-01-23T21:00:00Z
        and updatedAt le 2024-01-25T20:59:59Z
        and createdAt ge 2022-09-30T21:00:00Z
&$top=50
&$orderby=updatedAt,id
&$skip=0
```

Запрос возвращает заявки:

- обновлённые не раньше `24.01.2024 00:00 МСК` (`2024-01-23T21:00:00Z`);
- обновлённые не позже `25.01.2024 23:59:59 МСК` (`2024-01-25T20:59:59Z`);
- созданные после `01.10.2022 00:00 МСК` (`2022-09-30T21:00:00Z`), если нужно ограничить выборку по дате создания;
- первые 50 записей, начиная с позиции 0;
- отсортированные по дате обновления и ID: `updatedAt,id`.

Все списки рекомендуется получать порциями по 50 записей. Не запрашивайте полный список без ограничения количества: тяжелые запросы увеличивают нагрузку на сервер и могут привести к временной блокировке пользователя системой.

# Синхронизация заявок API 2.0

Этот сценарий предназначен для 1С/ERP, которая должна получать изменения заявок
из CARGO.RUN и надёжно подтверждать их обработку.

## 1. Какие каналы нужны

| Канал | Назначение |
|---|---|
| `GET /api/bids/GetListForExternal` | Первичная загрузка, статусы, удаления, периодическая сверка |
| `POST/GET /api/tasks/queue` | Оперативное асинхронное получение накопленных изменений |

API 2.0 не заменяет `GetListForExternal`: он не гарантирует все смены статуса и
удаления.

## 2. Первичная загрузка

1. Зафиксируйте `windowEnd` перед началом выборки.
2. Прочитайте все страницы `GetListForExternal` до `windowEnd`.
3. Используйте `$orderby=updatedAt,id`, фиксированный `$top` и последовательный `$skip`.
4. Сохраняйте заявки по `id` CARGO.RUN. `externalId` не уникален.
5. Обрабатывайте `isDeleted = true` как изменение.
6. Продвигайте курсор только после успешной обработки всех страниц.

## 3. Оперативный цикл

1. Отдельный пользователь интеграции вызывает `POST /api/tasks/queue` с `Read` для `Bid`.
2. Вызов выполняется чаще одного раза в час. Окно изменений в текущей реализации
   равно одному часу.
3. Клиент сохраняет ID задания и ожидает `Completed` или `Error`.
4. Клиент проверяет `objects[].status` и сохраняет каждый `Success` вместе с `id` и `version`.
5. После фиксации в локальной транзакции клиент отправляет `ReadConfirmation`.
6. При `VersionMismatch` клиент повторно читает объект и подтверждает уже новую версию.

Несколько быстрых изменений одной заявки могут объединиться. API 2.0 передаёт
последнюю версию объекта, а не журнал всех промежуточных событий.

## 4. Защита от эха

Изменения, записанные тем же пользователем синхронизации, не ставятся ему в очередь
входящих изменений. Поэтому:

- используйте для интеграции отдельного пользователя;
- не ожидайте, что собственная запись вернётся через `Read`;
- после изменяющего запроса проверяйте ответ или повторно читайте объект по `id`.

## 5. Контрольная сверка

Выполняйте её:

- по расписанию;
- после перерыва в работе длиннее часа;
- после ошибки `Read`, `ReadConfirmation` или локальной транзакции;
- для получения гарантированных смен статуса и удалений.

Выборка должна иметь фиксированные границы по `updatedAt`, небольшое перекрытие и дедупликацию
по `id + updatedAt`. Подробности: [Синхронизация справочников и заявок](./sync.md).

## 6. Восстановление

Если курсор API 2.0 потерян, не пытайтесь восстановить его из ID последнего задания.
Запустите контрольную выборку `GetListForExternal` от последней надёжно сохранённой границы.

Технический контракт очереди: [Асинхронная очередь API 2.0](../api/async-tasks.md).

# Пример интеграции CARGO.RUN и 1С

Этот пример описывает типовую схему интеграции между:

- **CARGO.RUN** — система управления перевозками;
- **1С** — учётная система Клиента.

Пример показывает, как:

- настроить обмен справочниками и заявками;
- организовать инкрементальную синхронизацию;
- обрабатывать обновления заявок из CARGO.RUN в 1С;
- решать конфликты изменений.

---

## 1. Общая архитектура интеграции

В 1С рекомендуется реализовать отдельный слой для интеграции со следующей логикой:

1. **Создать дополнительную таблицу для интеграции**, в которой хранить:
   - ссылки на элементы справочников (водитель, машина, прицеп, контрагент, организация);
   - ссылки на заявки;
   - идентификатор объекта в CARGO.RUN (`id`);
   - внешний атрибут `externalId`, если он нужен проекту, но не как уникальный ключ;
   - дату обновления объекта в CARGO.RUN (`updatedAt`);
   - дату обновления объекта в 1С.

2. При создании или обновлении:
   - элемента справочника,
   - заявки,

   необходимо:

   - записывать запись в интеграционную таблицу;
   - при первом создании объекта в CARGO.RUN сохранять его `id` в 1С;
   - при последующих обновлениях — всегда передавать этот `id` в запросах к API CARGO.RUN.

`externalId` заявки не уникален. Первичный ключ интеграционной таблицы должен
однозначно связывать локальный объект с `id` CARGO.RUN.

3. **Периодически (например, раз в 15 минут)**:
   - выбирать из интеграционной таблицы все элементы справочников и заявки, созданные или изменённые за этот период;
   - отправлять их в CARGO.RUN через соответствующие методы (`/api/driver/apply`, `/api/car/apply`, `/api/trailer/apply`, `/api/truckingbids/apply` и т.д.).

4. В 1С у каждого элемента справочника и заявки рекомендуется хранить две даты:
   - «Дата обновления в CARGO.RUN»;
   - «Дата обновления в 1С».

Эти даты используются для анализа изменений и разрешения конфликтов.

---

## 2. Обновление данных заявок из CARGO.RUN в 1С

Если данные заявки могут изменяться в CARGO.RUN (например, фактические времена
въезда/выезда, пробег, факт выполнения), 1С должна получать оперативные изменения
через API 2.0 и периодически выполнять контрольную выборку `GetListForExternal`.
Очередь API 2.0 не гарантирует каждую смену статуса и удаление. См.
[Синхронизация заявок API 2.0](./async-sync-v2.md).

### 2.1. Основные шаги

1. При создании или обновлении заявки в 1С сохранять:
   - дату обновления заявки в 1С;
   - последнюю известную дату обновления заявки в CARGO.RUN (`updatedAt`).

2. В CARGO.RUN получать список заявок и их дату обновления `updatedAt`.

3. Для выполненных заявок особый интерес представляют:

   - статус заявки: `status = "Done"`;
   - фактический километраж: `factMileage`;
   - по точкам загрузки/выгрузки:
     - дата въезда в геозону: `bidPoints -> autoEnteredAt`;
     - дата выезда из геозоны: `bidPoints -> autoLeavedAt`.

### 2.2. Пример запроса по выполненным заявкам

Пример OData-запроса (с фильтрацией по статусу и дате обновления):

```text
GET /api/bids/GetListForExternal
  ?$filter=Status eq 'Done'
           and updatedAt gt 2019-11-20T06:00:00Z
  &$orderby=updatedAt,id
  &$top=50
  &$skip=0
```

После получения данных:

- если дата обновления заявки в CARGO.RUN (`updatedAt`) более поздняя, чем дата обновления заявки в 1С — необходимо обновить данные заявки в 1С.

### 2.3. Пользовательские поля (extendedProperties)

При получении данных по заявке пользовательские поля передаются в массиве `extendedProperties`:

```json
"extendedProperties": [
  {
    "propertyName": "Due_date",
    "value": "12"
  }
]
```

- `propertyName` — имя пользовательского поля;
- `value` — значение, заданное пользователем.

### 2.4. Пользовательские справочники (typeOptions)

Пользовательские справочники заявки описываются в массиве `typeOptions`:

```json
"typeOptions": [
  {
    "id": 3795270,
    "entityOptionId": 3794317
  }
]
```

- `id` — идентификатор справочника в организации клиента;
- `entityOptionId` — идентификатор справочника в CARGO.RUN.

---

## 3. Варианты обновления данных заявки

При обновлении данных по заявке из CARGO.RUN в 1С возможны четыре базовые ситуации:

1. Заявка не изменилась в CARGO.RUN, не изменилась в 1С.
2. Заявка не изменилась в CARGO.RUN, изменилась в 1С.
3. Заявка изменилась в CARGO.RUN, не изменилась в 1С.
4. Заявка изменилась и в CARGO.RUN, и в 1С.

Для анализа используются три даты:

- дата обновления заявки в CARGO.RUN;
- дата обновления заявки в 1С;
- дата последней синхронизации.

Ниже рассмотрены все варианты.

### 3.1. Заявка не изменилась в CARGO.RUN, не изменилась в 1С

Условия:

- Дата последней синхронизации > Дата обновления заявки в CARGO.RUN.
- Дата последней синхронизации > Дата обновления заявки в 1С.

Итог:

- Обновление данных не требуется.

---

### 3.2. Заявка не изменилась в CARGO.RUN, изменилась в 1С

Условия:

- дата последней синхронизации не меньше `updatedAt` заявки CARGO.RUN;
- дата изменения заявки в 1С больше даты последней синхронизации.

Итог:

- если 1С является владельцем изменённых полей, отправить изменения в CARGO.RUN;
- перечитать заявку и сохранить новое `updatedAt`;
- помнить, что `Apply` полностью перезаписывает заявку: перечитать объект, объединить
  изменения и не отправлять устаревшие значения полей, владельцем которых является CARGO.RUN.

---

### 3.3. Заявка изменилась в CARGO.RUN, не изменилась в 1С

Условия:

- `updatedAt` заявки CARGO.RUN больше даты последней синхронизации;
- дата изменения заявки в 1С не больше даты последней синхронизации.

Итог:

- обновить запись 1С данными CARGO.RUN;
- сохранить полученное `updatedAt` и время успешной синхронизации.

---

### 3.4. Заявка изменилась и в CARGO.RUN, и в 1С

Условия:

- `updatedAt` заявки CARGO.RUN больше даты последней синхронизации;
- дата изменения заявки в 1С больше даты последней синхронизации.

Это конфликт. Не выбирайте победителя только по более позднему времени: часы систем
могут различаться, а системы могут владеть разными полями.

Рекомендуемый порядок:

1. Разделить поля по владельцу. Например, 1С может владеть номером первичного
   документа и данными оплаты, а CARGO.RUN — оперативным статусом, фактическими
   событиями и назначенной техникой. Конкретную матрицу утверждают до запуска.
2. Автоматически объединять только изменения в непересекающихся группах полей.
3. Если одно поле изменено с обеих сторон, создать запись конфликта и передать её
   ответственному сотруднику; не выполнять `Apply` автоматически.
4. После разрешения перечитать заявку, сохранить итоговое `updatedAt` и зафиксировать
   время успешной синхронизации.

### 3.5. Обязательная матрица владельцев данных

До внедрения двусторонней синхронизации зафиксируйте для каждой группы полей:

| Группа | Владелец | Допустимое направление | Правило конфликта |
|---|---|---|---|
| Статус исполнения | CARGO.RUN | CARGO.RUN → 1С | Не перезаписывать из 1С |
| Фактические события точек | CARGO.RUN | CARGO.RUN → 1С | Не перезаписывать из 1С |
| Данные оплаты | Утверждается проектом | Одно направление | Ручное разрешение при расхождении |
| Пользовательские поля | Для каждого поля отдельно | По утверждённой схеме | По владельцу поля |

Таблица выше — безопасный шаблон, а не универсальное распределение ответственности.
Добавьте в неё все поля, которые интеграция разрешает изменять.

# Обзор API CARGO.RUN

## 1. Стиль и структура API

API CARGO.RUN построен на REST и использует:

- протокол HTTPS,
- методы HTTP (`GET`, `POST`),
- формат JSON,
- авторизацию через токен.

Все структуры данных, обязательные поля и параметры приведены в соответствующих разделах API Reference. Если для метода нужна модель запроса или ответа, она описывается рядом с методом.

## 2. Авторизация

Большинство методов требует токен:

```
Authorization: Bearer <token>
```

Полное описание авторизации приведено в разделе:
[Auth API](./auth.md)

---

## 3. Модели и данные

Структуры объектов описаны в разделах конкретных методов: таблицах полей, примерах JSON и перечнях допустимых значений.

Для оперативной инкрементальной синхронизации заявок используйте асинхронную
очередь API 2.0:

```
POST /api/tasks/queue
GET /api/tasks/queue?id={taskId}
```

Для первичной загрузки, получения статусов и удалений, а также контрольной сверки


API-методы по справочникам не поддерживают фильтрацию по `updatedAt`.

[Синхронизация заявок API 2.0](../integration/async-sync-v2.md).

## 4. Правила работы с API

### 4.1. Формат данных

API принимает и возвращает JSON.
Подробные правила работы с форматами описаны в:
[Форматы данных](../formats.md)

---

### 4.2. Даты и время

В документации даты обозначаются типом:

```
string (date-time)
```

Это формат ISO 8601.
Используйте формат ISO 8601 со смещением часового пояса. В интеграционных примерах обычно используется UTC (`Z` или `+00:00`).

---

### 4.3. Пагинация и фильтрация

Поддерживаются параметры OData:

- `$filter`
- `$orderby`
- `$top`
- `$skip`

Они применимы только к методам, в описании которых явно указаны соответствующие query-параметры.

### 4.4. Регистрозависимость URL

API CARGO.RUN регистронезависим.
Однако для единообразия во всей документации используется **нижний регистр URL**.

---

### 4.5. Ошибки

Универсальная JSON-структура ошибок не используется для всех методов.

API возвращает:

- HTTP 4xx при бизнес‑ограничениях,
- текстовое пояснение причины ошибки.

---

### 4.6. Используемые HTTP‑методы

API CARGO.RUN использует **только два HTTP‑метода**:

- **GET** — получение данных
- **POST** — создание, обновление, удаление, отмена, восстановление, смена статусов

Методы `DELETE`, `PUT`, `PATCH` **не используются**.

Примеры POST-команд:

```
POST /api/bids/restore
POST /api/truckingbids/revert
POST /api/truckingbids/setstatus
POST /api/truckingbids/forcecomplete
```

### 4.7. Общий паттерн создания и обновления объектов

```
{
  "id": 0,
  ...
}
```

#### Обновление объекта


# Авторизация и доступ к API

Этот раздел описывает, как получить доступ к API CARGO.RUN и как передавать токен авторизации в запросах.

---

## 1. Общие принципы

Доступ к API CARGO.RUN защищён с помощью **JWT-токена**, который передаётся в HTTP-заголовке:

```http
Authorization: Bearer <access_token>
```

Заголовок передается во все методы, которым требуется авторизация. Формат значения: слово `Bearer`, пробел и токен доступа.

---

## 2. Базовый URL

Базовый URL API определяется для конкретного клиента при подключении:

```text
https://api.app.cargorun.ru/
https://api.test.cargorun.ru/
https://api.<customer>.cargorun.ru/
```

Во всех примерах далее используется абстрактный `<baseUrl>`.

---

## 3. Получение токена доступа

Для получения токена используется метод:

```
POST /api/Account/GenerateToken
```

### 3.1. Модель запроса

```json
{
  "userName": "string",
  "password": "string",
  "code": "string"
}
```

Для интеграции поле `code` может быть проигнорировано. Используется для авторизации водителей.

Полученный токен имеет ограниченный срок действия и не требует повторного запроса
при каждой операции. До его истечения или после ответа `401` обновите пару токенов.

Не вычисляйте срок действия самостоятельно: используйте `accessToken.expiresIn`
из ответа. Значение задаётся сервером и может отличаться между средами.


### 3.2. Пример запроса

```http
POST <baseUrl>/api/Account/GenerateToken
Content-Type: application/json

{
  "userName": "user@example.com",
  "password": "P@ssw0rd",
  "code": "999999"
}
```

### 3.3. Успешный ответ

Основные поля ответа:

| Поле | Тип | Описание |
|---|---|---|
| `accessToken.token` | `string` | JWT для заголовка `Authorization` |
| `accessToken.expiresIn` | `integer` | Срок действия access token в секундах |
| `refreshToken` | `string` | Токен для обновления пары токенов |
| `requiresTwoFactor` | `boolean` | Требуется ли второй фактор |
| `twoFactorToken` | `object?` | Временный токен второго фактора, если он требуется |
| `currentUser` | `object?` | Данные текущего пользователя |

Сокращённый пример без пользовательских данных:

```json
{
  "accessToken": {
    "token": "<jwt>",
    "expiresIn": 1800
  },
  "refreshToken": "<refresh_token>",
  "requiresTwoFactor": false,
  "twoFactorToken": null
}
```

### 3.4. Ограничения метода

Метод `/api/Account/GenerateToken` не предназначен для регулярного или частого вызова. На стороне сервера действуют ограничения (cooldown), и при слишком частом запросе токена сервер может вернуть ошибку `429`.

Причина введения ограничения:

- метод должен использоваться только для начальной авторизации пользователя;
- дальнейшая работа с API должна выполняться через механизм обновления токена (`RefreshToken`).

---

## 4. Обновление токена

Для обновления токена необходимо использовать метод:

```
POST /api/Account/RefreshToken
```

### 4.1. Модель запроса

```json
{
  "accessToken": "string",
  "refreshToken": "string"
}
```

### 4.2. Пример запроса

```http
POST <baseUrl>/api/Account/RefreshToken
Content-Type: application/json

{
  "accessToken": "<старый_access_token>",
  "refreshToken": "<refresh_token>"
}
```

При успехе метод возвращает новую пару в том же формате. Сохраните оба новых
значения атомарно; не продолжайте использовать прежний refresh token, если сервер
вернул новый.

---

## 5. Передача токена в запросах

```http
Authorization: Bearer <access_token>
```

Пример:

```http
GET <baseUrl>/api/bids/GetListForExternal
Authorization: Bearer eyJhbGciOiJIUzI1...
```

---

## 6. Ошибки авторизации

### 401 Unauthorized
- отсутствует заголовок
- токен просрочен или недействителен

### 403 Forbidden
- недостаточно прав

---

## 7. Рекомендации по безопасности

- не хранить токены в логах;
- ограничить доступ к файлам конфигурации;
- использовать только HTTPS;
- при утечке токена немедленно перевыпустить.

# 1. Создание и обновление заявки

## 1.1. Полное создание или обновление заявки

```http
POST /api/truckingbids/apply
```

### Назначение

- Создание новой заявки (`id = 0`)
- Полное обновление существующей заявки (`id > 0`)

В теле запроса передается полная модель заявки. При каждом вызове `Apply` модель
перезаписывает сохранённое состояние заявки. Для обновления (`id > 0`) сначала
получите актуальную карточку, объедините изменения и передайте все значения, которые
должны сохраниться. Для изменения отдельных полей используйте `Patch`.

`externalId` не уникален и не обеспечивает идемпотентность. После создания сохраните
возвращённый `id` CARGO.RUN и используйте именно его для всех последующих операций.

## 1.2. Частичное обновление заявки (Patch) { #bid-patch }

```http
POST /api/truckingbids/patch
```

### Назначение

- обновление только изменённых полей заявки.

### Ограничения

- нельзя частично изменить вложенные структуры (`bidPoints`, `cargos`, `typeOptions` и др.);
- если нужно изменить маршрутные точки — необходимо передать **весь массив** `bidPoints`, включая неизменённые точки.

## 4.2. Получение списка заявок (инкрементальная синхронизация)

```http
GET /api/bids/getlistforexternal
```

Метод возвращает список заявок по фильтру для внешних сервисов с более подробной информацией. Используется OData-формат параметров.

У каждой заявки есть поле `updatedAt` — дата последнего изменения заявки в CARGO.RUN.
Для инкрементальной синхронизации обрабатывайте фиксированные окна времени с
перекрытием и дедупликацией по `id` и `updatedAt`. Не продвигайте границу окна до
успешной обработки всех страниц. Подробный алгоритм приведён в разделе
[Синхронизация данных](../integration/sync.md#sync-updated-at).

Поддерживает:

- `$filter`
- `$orderby`
- `$top`
- `$skip`

Пример запроса:

```http
GET /api/bids/GetListForExternal
  ?$filter=updatedAt ge 2024-01-23T21:00:00Z
           and updatedAt le 2024-01-25T20:59:59Z
           and createdAt ge 2022-09-30T21:00:00Z
  &$top=50
  &$orderby=updatedAt
  &$skip=0
```

Запрос возвращает заявки:

- дата обновления которых больше или равна `24.01.2024 00:00 МСК` (`2024-01-23T21:00:00Z`);
- дата обновления которых меньше или равна `25.01.2024 23:59:59 МСК` (`2024-01-25T20:59:59Z`);
- дата создания которых больше или равна `01.10.2022 00:00 МСК` (`2022-09-30T21:00:00Z`), если нужно ограничить выборку по дате создания;
- первые 50 записей, начиная с позиции 0;
- отсортированные по дате обновления `updatedAt`.

Все списки необходимо получать порциями по 50 записей для минимизации нагрузки на сервер. Если получать полные списки без ограничения количества, пользователь может быть временно заблокирован системой.

Подробное описание в:

- [Синхронизация данных](../integration/sync.md)

# 6. Ошибки

Возможные ошибки:

- невалидные данные (`paymentTypeId`, `ndsTypeId`, элементы геозон и т.д.);
- попытка удалить заявку без предварительного `revert`;
- частичное обновление вложенных структур через `/patch`.

Поведение API:

- ошибки бизнес-валидации возвращаются с HTTP-статусом `400`;
- тело ошибки может быть обычным текстом или JSON-объектом `ValidationApiResult`;
- не повторяйте запрос с теми же данными после `400`: сначала исправьте payload;
- при `401` обновите токен и повторите запрос один раз;
- при `429` или временной ошибке `5xx` используйте ограниченные повторы с увеличивающейся задержкой.

Общий формат обработки ошибок описан в разделе [Форматы данных](../formats.md#api-errors).

# Асинхронная очередь API 2.0

API 2.0 выполняет чтение и запись объектов в фоновой очереди. Обычный
клиент 1С/ERP работает с методами:

```http
POST /api/tasks/queue
GET  /api/tasks/queue?id={taskId}
```

`/api/iris/queue` — алиас тех же методов. В новых интеграциях используйте
`/api/tasks/queue`.

!!! warning
    `/api/integrations/Tasks/Queue` относится к отдельному партнёрскому API с другой
    авторизацией. Не используйте его вместо `/api/tasks/queue`.

## 1. Подготовка

Администратор организации должен создать настройку внешней системы и привязать
к ней отдельного пользователя:

```http
GET  /api/SyncSystems/Get
POST /api/SyncSystems/Apply
POST /api/SyncSystems/Delete
```

Основные поля `SyncSystemModel`:

| Поле | Значение |
|---|---|
| `id` | `0` для новой настройки, ID для изменения |
| `userId` | Пользователь, от имени которого работает интеграция |
| `behavior` | `0` — очистка при чтении; `1` — очистка только после `ReadConfirmation` |
| `trackingType` | `0` — не отслеживать; `1` — все изменения; `2` — изменения экспедиции |
| `callback.target` | HTTPS URL для уведомления о завершении задания |
| `callback.secret` | Секрет HMAC-SHA256; не передавайте его в журналах |

Для надёжной синхронизации используйте `behavior = 1` и `trackingType = 1`.

## 2. Постановка задания

```http
POST /api/tasks/queue
Authorization: Bearer <accessToken>
Idempotency-Key: sync-bids-20261012-1200
Content-Type: application/json
```

```json
{
  "commands": [
    {
      "action": 1,
      "objects": [
        {
          "type": 1,
          "modelType": 0
        }
      ]
    }
  ]
}
```

Пример ставит в очередь чтение накопленных изменений заявок. `Idempotency-Key`
необязателен, имеет длину не более 100 символов и в течение 24 часов возвращает
те же задания для повторного запроса.

Сервер возвращает HTTP `202 Accepted`:

```json
{
  "latencyMsec": 25,
  "enqueuedInMsec": 3,
  "commands": [
    {
      "id": 731245,
      "action": 1,
      "status": 0,
      "readyInMsec": 25,
      "message": null
    }
  ]
}
```

Каждая команда ставится в очередь независимо. Проверяйте `commands[].status`: `0` —
успех, `1` — команда не попала в очередь. `commands[].id` — ID задания, а не ID заявки.

## 3. Действия

| Код | Имя | Назначение |
|---:|---|---|
| `0` | `Write` | Создание или полное обновление |
| `1` | `Read` | Чтение объектов или накопленных изменений |
| `2` | `ReadConfirmation` | Подтверждение обработанной версии |
| `3` | `ReadQuery` | Чтение по OData-запросу |
| `4` | `Delete` | Удаление по ID CARGO.RUN |

Типы объектов: `1` — `Bid`, `2` — `DistributionBid`, `3` — `Car`, `4` — `Trailer`,
`5` — `Driver`, `6` — `Counterparty`.

Основные поля `objects[]`:

| Поле | Правило |
|---|---|
| `id` | Внутренний ID CARGO.RUN; `null`/`0` при `Write` создаёт объект |
| `key` | Внешний корреляционный ключ до 64 символов; не уникален и не заменяет `id` |
| `version` | UUID версии; передача при `Write` включает проверку конкурентного изменения |
| `modelType` | `0` — основная модель; другие значения используйте только в описанном сценарии |
| `body` | Полная модель для `Write` |
| `query` | OData-запрос для `ReadQuery`; в этом объекте `id`, `version` и `key` должны быть пустыми |

`externalId` заявки и `objects[].key` не уникальны. Обновление, чтение, подтверждение
и удаление выполняйте по `objects[].id` CARGO.RUN.

## 4. Получение результата

```http
GET /api/tasks/queue?id=731245
Authorization: Bearer <accessToken>
```

Статусы задания: `0` — `Awaiting`, `1` — `InProgress`, `2` — `Completed`, `3` — `Error`.

- При `InProgress` сервер передаёт `Retry-After` в секундах.
- При `Awaiting` ориентируйтесь на `nextRetryAt`.
- `Completed` не означает успех всех объектов. Проверьте каждый `objects[].status`.
- Неизвестное или недоступное задание может вернуть HTTP `200` с `null`.

Статусы объекта: `0` — `Created`, `1` — `Success`, `2` — `Error`, `3` — `VersionMismatch`.
При `VersionMismatch` в ответе передаётся текущая версия: перечитайте объект и не
подтверждайте устаревшую версию.

Обработка задания выполняется до трёх раз. После ошибок используются задержки 5 и 10
секунд. Завершённые задания хранятся примерно три дня; забирайте результат без отлагательств.

## 5. Надёжное чтение с подтверждением

Для `behavior = 1`:

1. поставьте `Read` для типа `Bid`;
2. дождитесь `Completed`;
3. надёжно сохраните каждый успешный объект вместе с `id` и `version`;
4. только после успешной локальной транзакции отправьте `ReadConfirmation`:

```json
{
  "commands": [
    {
      "action": 2,
      "objects": [
        {
          "type": 1,
          "modelType": 0,
          "id": 123456,
          "version": "2f1ac0f8-1da7-4e74-b69d-1a94de150803"
        }
      ]
    }
  ]
}
```

Изменения, сделанные тем же пользователем синхронизации, не возвращаются ему как
входящие изменения. Это предотвращает эхо синхронизации.

## 6. Callback

Если в `SyncSystemModel` задан `callback.target`, CARGO.RUN отправляет `POST` после завершения
задания. Проверяйте:

```text
HMAC_SHA256(callback.secret, "<timestamp>.<raw-json-body>")
```

Заголовки: `X-Cargorun-Task-Id`, `X-Cargorun-Webhook-Event`,
`X-Cargorun-Webhook-Timestamp`, `X-Cargorun-Webhook-Signature: sha256=<hex>`.

Callback выполняется до пяти раз с задержками 10, 20, 40 и 80 секунд. Повтор
выполняется при сетевой ошибке, HTTP `408`, `429` или `5xx`.

`callbackStatus` и счётчики callback возвращаются в `GET /api/tasks/queue`.

## 7. Границы гарантий

- В выборку `Read` попадают накопленные изменения не старше одного часа. Это
  намеренное ограничение. Вызывайте синхронизацию чаще одного раза в час.
- Несколько изменений одного объекта могут объединяться: клиент получит последнюю
  версию, а не журнал каждого промежуточного события.
- API 2.0 пока не гарантирует доставку всех смен статуса и удалений. Для
  них используйте контрольную синхронизацию через `GET /api/bids/GetListForExternal`.

Полный алгоритм: [Синхронизация заявок API 2.0](../integration/async-sync-v2.md).

# Справочники API CARGO.RUN

Этот раздел описывает методы работы со справочниками, которые участвуют в интеграции:

- водители;
- автомобили;

## 1. Общие принципы

Для всех справочников используются общие правила:

- формат данных — JSON;
- авторизация — по токену (см. [Auth API](../api/auth.md));
- операции создания и обновления выполняются по паттерну `Apply`:
  - `id = 0` — создание;
  - `id > 0` — обновление;
- операции удаления и восстановления выполняются через `POST`-методы (`.../delete`, `.../restore`);
- при ошибках валидации возвращается HTTP 4xx и текстовое описание ошибки.

Минимальные требования к полям см. в:


Список общих справочников со значениями можно получить так:

```http
GET /api/catalogs/getSimple?$filter=externalId eq null&$orderby=id desc
```

В URL пробелы кодируются как `%20`:

```http
https://app.cargorun.ru/api/catalogs/getSimple?$filter=externalId%20eq%20null&$orderby=id%20desc
```

| `$top` | Ограничение количества записей |

# Пользовательские справочники API

Пользовательские, или кастомные, справочники — это несистемные справочники, которые клиент создает в своем аккаунте CARGO.RUN. Они используются только внутри организации клиента и могут быть привязаны к заявкам или заказам.

В выгрузке заявок и заказов такие значения приходят в массиве `typeOptions`.

---

## 1. Как связаны `typeOptions` и справочники

В методах:

```http
GET /api/bids/GetListForExternal
GET /api/DistributionBids/GetListForExternal
```

может приходить массив:

```json
{
  "typeOptions": [
    {
      "id": 129619121,
      "entityOptionId": 126364242
    }
  ]
}
```

Поля `TypeOptionModel`:

| Поле | Тип | Описание |
|---|---|---|
| `id` | `long` | ID элемента справочника |
| `entityOptionId` | `long` | ID настройки/свойства справочника, к которому относится значение |

Чтобы получить текстовое значение элемента справочника, используйте `id` из `typeOptions[]` и запросите элемент через `GET /api/Catalogs/GetItems`.

```http
GET /api/Catalogs/GetItems?$filter=id eq 129619121
```

В ответе будет элемент справочника, где значение лежит в `displayName`.

---

## 2. Получение списка справочников

```http
GET /api/Catalogs/GetCatalogs
```

# Электронные транспортные накладные (ЭТРН)

Этот раздел описывает методы API CARGO.RUN для работы с электронными транспортными накладными (ЭТРН) со стороны внешних систем, включая 1С и провайдеров ЭТРН.

- [Обзор API](./overview.md)

## 1. Методы для 1С

### 1.1. Получение списка титулов со статусами

```http
GET /api/1c/bills/gettitles
```

#### Назначение

Получение списка титулов ЭТРН с их текущими статусами в формате OData.

Метод возвращает коллекцию `TitleExternalModel`, в которой для каждого титула указаны:

- `id` — идентификатор титула;
- `type` — тип титула (`TitleType`);
- `status` — статус (`WaybillTitleStatus`);
- `statusDate` — дата и время изменения статуса;
- `bill` — данные по накладной (`WaybillExternalModel`).

[Статусы титулов ЭТРН](../statuses.md)

#### Параметры запроса

Метод поддерживает стандартные OData-параметры:

- `$filter` — фильтр по полям модели `TitleExternalModel`;
- `$orderBy` — сортировка;
- `$top` — ограничение количества;
- `$skip` — смещение;
- `$count` — возврат количества записей;
- `$select` — выбор полей.

Примеры:

1. Получить все титулы в статусе `ReceivedOrCreated`:

```text
GET /api/1c/bills/gettitles?$filter=status eq 'ReceivedOrCreated'
```

2. Получить первые 50 титулов, отсортированных по дате статуса:

```text
GET /api/1c/bills/gettitles?$orderby=statusDate desc&$top=50
```

### 1.2. Получение титула по заявке

```http
GET /api/1c/Bills/GetTitle?titleId={titleId}&bidId={bidId}&bidExternalId={bidExternalId}
```

#### Назначение

Получение данных одного титула ЭТРН.

Метод может искать титул:

- по идентификатору заявки и по идентификатору титула;
- по внешнему идентификатору заявки и по идентификатору титула.

#### Параметры запроса

Метод поддерживает следующие query-параметры:

- `titleId` — идентификатор титула (int64);
- `bidId` — идентификатор заявки (int64);
- `bidExternalId` — внешний идентификатор заявки (string).

Ответ — модель `TitleWithRemarksExternalModel`, содержащая:

- данные титула;
- статус и дату статуса;
- комментарии и замечания, если есть.

### 1.3. Смена статуса титула

```http
POST /api/1c/bills/applystatus
```

#### Назначение

Изменение статуса титула ЭТРН со стороны внешней системы.

Метод позволяет:

- подтвердить титул;
- отклонить титул;
- передать новый статус обработки титула в CARGO.RUN.

#### Тело запроса

Тело описано моделью `TitleStatusApplyExternalModel`:

Поля:

- `id` — идентификатор титула, обязательное поле;

- `bidId` — идентификатор заявки;
- `bidExternalId` — внешний идентификатор заявки.

#### Поддерживаемые значения статуса

Список статусов задаётся enum `WaybillTitleStatus`:

| Значение | Описание |

# Транзакции заправок

Метод загрузки транзакций с АЗС для формирования отчёта план‑факт по посещению АЗС и сопоставления с маршрутом.

- Запрос может выполняться как с `X-Api-Key`, так и с JWT.
- При запросе с `X-Api-Key` без JWT — доступ ко всем транзакциям.
- При запросе с JWT — доступ ограничен текущей организацией; чужие трекеры отфильтровываются.

---

## 1. Создание транзакций

```http
POST /api/refuelingTransactions/create
Content-Type: application/json
```

### Тело запроса

```json
{
  "transactions": [
    {
      "deviceNumber": "string",
      "cardNumber": "string",
      "externalId": "string",
      "createdAt": "2025-12-01T12:42",
      "volume": 1.0,
      "cost": 1.0,
      "description": "string",
      "address": "string",
      "x": 55.23123,
      "y": 69.42
    }
  ]
}
```

### Обязательность и ограничения полей

- Идентификатор: обязателен один из `deviceNumber` или `cardNumber` или `externalId`. Если не указан ни один — элемент пропускается и вернётся в `errors`.
- Остальные обязательные поля: `createdAt`, `volume`, `cost`, `address`, `x`, `y`.
- `deviceNumber`: max 128 символов.
- `cardNumber`: max 128 символов.
- `externalId`: max 512 символов.
- `createdAt`: не ранее 2023 года, не позже текущее время + 6 часов (UTC).
- `address`: max 1024 символа.
- `description`: необязательное, max 2048 символов.
- `x` (долгота): диапазон [-90, 90], точность до 6 знаков после запятой.
- `y` (широта): диапазон [-180, 180], точность до 6 знаков после запятой.
- `transactions`: максимум 4096 элементов.

### Идемпотентность и ключи

Транзакция определяется одним из ключей (приоритет сверху вниз):

1. `deviceNumber` + `createdAt`
2. `cardNumber` + `createdAt`
3. `externalId` + `createdAt`

- Если указаны все три — используется `deviceNumber`, остальные игнорируются.
- При наличии записи с тем же ключом данные обновляются, а не дублируются.
- Если внутри одного запроса есть несколько элементов с одинаковым ключом, применяется последний по порядку.
- Обновление существующих транзакций возможно только для дат не старше четырёх месяцев; более поздние транзакции вернутся с ошибкой.
- Если `deviceNumber` или `cardNumber` не существуют в системе, такие транзакции просто игнорируются (не попадут в `errors`).

---

## 2. Ответы сервера

- `201` — все транзакции сохранены; тело ответа пустое.
- `200` — часть транзакций не принята:

```json
{
  "errors": [
    {
      "message": "Причина, почему не создалась транзакция",
      "transaction": { }
    }
  ]
}
```

- `400` или `500` — текстовая ошибка; ни одна транзакция не сохранена.
- `401` — не указан `X-Api-Key` и отсутствует валидный токен.
- `403` (если нет `X-Api-Key`) — недостаточно прав/нет нужной роли у пользователя.

---

## 3. Назначение и сценарии

- Загрузка транзакций с АЗС для отчёта план‑факт по маршруту.
- Поля `deviceNumber`/`cardNumber` позволяют связать транзакцию с трекером и топливной картой; `externalId` помогает дедуплицировать данные из внешних систем.
- Координаты и адрес используются для сопоставления с плановыми точками заправки на маршруте.

# Трекеры и привязка к транспортным средствам

Этот раздел описывает только те методы работы с трекерами, которые используются во внешней интеграции:

- привязка трекера к машине или прицепу;
- получение списка трекеров;
- отвязка трекера от машины или прицепа.

Общие принципы работы API описаны в:

- [Обзор API](../api/overview.md)
- [Auth API](../api/auth.md)

---

## 1. Привязка трекера к машине или прицепу

```http
POST /api/trackers/attach
```

### Назначение

Привязать трекер к конкретному транспортному средству:

- грузовому автомобилю;
- прицепу.

### Тело запроса

```json
{
  "id": 0,
  "entityId": 0,
  "type": "Car"
}
```

Поля:

- `id` — идентификатор трекера в CARGO.RUN;
- `entityId` — идентификатор объекта (машина или прицеп);
- `type` — тип объекта:
  - `Car` — грузовой автомобиль;
  - `Trailer` — прицеп.

### Комментарии

- Для привязки необходимо знать **id трекера** и **id машины/прицепа**.
- Идентификатор трекера можно получить через метод `GET /api/trackers/get`, отфильтровав по номеру устройства (`deviceNumber`).

Пример (поиск трекера по номеру устройства в OData):

```text
GET /api/trackers/get?$filter=deviceNumber eq '1234567890'
```

Из полученного списка выбирается нужный трекер, и его `id` используется в теле запроса `POST /api/trackers/attach`.

---

## 2. Получение списка трекеров

```http
GET /api/trackers/get
```

### Назначение

Получение списка трекеров, доступных организации.
Метод поддерживает OData-фильтрацию.

### Параметры OData

Метод поддерживает стандартные параметры:

```text
?$filter=<string>
 &$orderBy=<string>
 &$top=<int>
 &$skip=<int>
 &$count=<bool>
 &$select=<string>
 &$expand=<string>
```

Примеры использования:

1. Поиск трекера по номеру устройства:

```text
GET /api/trackers/get?$filter=deviceNumber eq '1234567890'
```

2. Получение первых 50 трекеров:

```text
GET /api/trackers/get?$top=50
```

### Основные поля ответа

| Поле | Тип | Описание |
|---|---|---|
| `id` | `long` | ID трекера |
| `deviceNumber` | `string?` | Номер устройства / идентификатор трекера |
| `entityId` | `long?` | ID машины или прицепа, к которому привязан трекер |
| `type` | `string?` | Тип привязанного объекта: `Car` или `Trailer` |
| `isDeleted` | `boolean?` | Признак удаления, если поле возвращается в подключении |
| `updatedAt` | `date-time?` | Дата последнего изменения, если поле возвращается в подключении |

---

## 3. Отвязка трекера от машины или прицепа

```http
POST /api/trackers/attach
```

### Назначение

Отвязать трекер от машины или прицепа.

### Тело запроса

```json
{
  "id": 0,
  "entityId": null,
  "type": "Car"
}
```

Поля:

- `id` — идентификатор трекера;
- `entityId` — `null` (означает, что объект отвязывается);
- `type` — тип объекта:
  - `Car` — если трекер был привязан к машине;
  - `Trailer` — если трекер был привязан к прицепу.

### Комментарии

Для отвязки трекера необходимо:

- указать корректный `id` трекера;
- указать `entityId = null`;
- задать `type` в соответствии с тем, к какому типу объекта трекер был привязан (`Car` или `Trailer`).

---

## 4. Сводка используемых методов

| Метод | Описание |
|-------|----------|
| `POST /api/trackers/attach` | Привязка трекера к машине или прицепу |
| `GET /api/trackers/get` | Получение списка трекеров (с поддержкой OData) |
| `POST /api/trackers/attach` + `entityId = null` | Отвязка трекера от машины или прицепа |

## Приоритет источников

Если описания расходятся, агент не должен угадывать контракт. Используйте такой порядок:

1. описание конкретного метода в разделе API;
2. общие форматы, статусы и минимальные требования;
3. интеграционный сценарий;
4. пример payload.

Пример не отменяет таблицу полей. Если расхождение влияет на запрос, остановите
автоматическое выполнение и запросите подтверждение у владельца интеграции.

## Правила выполнения операций

1. Получите `<baseUrl>` и учётные данные из защищённой конфигурации. Не помещайте
   пароль, access token, refresh token и персональные данные в промпт, журнал или отчёт.
2. Получите токен через `GenerateToken`, затем обновляйте его через `RefreshToken`.
   Не вызывайте `GenerateToken` перед каждым запросом.
3. Перед созданием заявки сопоставьте справочники и проверьте все `...Id`.
4. Для новой заявки передайте `id = 0`; для обновления — фактический `id` CARGO.RUN.
5. Сохраните связь локального первичного ключа с возвращённым `id` CARGO.RUN, а также
   значение `updatedAt`. `externalId` не уникален и не подходит как ключ обновления.
6. После создания используйте возвращённый `id` для запуска, отмены или изменения заявки.
7. Считайте операции создания, обновления, смены статуса и удаления изменяющими данные.
   Перед их выполнением агент должен показать целевой объект и получить разрешение,
   если такое разрешение не было явно дано в исходной задаче.
8. После изменяющего запроса прочитайте объект повторно и проверьте результат.

## Повторы и ошибки

| Результат | Действие агента |
|---|---|
| `2xx` | Проверить тело ответа и сохранить идентификаторы/курсор синхронизации |
| `400` | Не повторять без изменений; разобрать текст или `errorMessage`, исправить payload |
| `401` | Обновить токен и повторить один раз |
| `403` | Остановиться и сообщить о нехватке прав |
| `404` | Проверить `<baseUrl>`, регистр пути и ID; не создавать замену автоматически |
| `409` | Повторно прочитать объект и разрешить конфликт с участием владельца данных |
| `429`, `5xx` | Ограниченные повторы с экспоненциальной задержкой и случайным сдвигом |

## Инкрементальная синхронизация

- Для оперативного обмена используйте асинхронную очередь API 2.0 и подтверждайте
  обработанные версии через `ReadConfirmation`.
- Вызывайте чтение API 2.0 чаще одного раза в час: текущее окно изменений намеренно
  ограничено одним часом, а несколько изменений объекта могут объединяться в последнее.
- API 2.0 пока не гарантирует каждую смену статуса и удаление. Получайте заявки через
  `GET /api/bids/GetListForExternal` порциями по 50 записей для начальной загрузки и
  контрольной сверки.
- Используйте фильтр по `updatedAt` и стабильную сортировку, поддерживаемую методом.
- Не продвигайте сохранённую верхнюю границу синхронизации, пока не обработаны все страницы.
- Делайте небольшое перекрытие временных окон и устраняйте дубликаты по `id` и `updatedAt`.
- Обрабатывайте `isDeleted`: удалённая заявка также является изменением.
- Периодически выполняйте контрольную сверку, а не полагайтесь только на последний курсор.

Подробный алгоритм: [Синхронизация заявок API 2.0](./integration/async-sync-v2.md).

## Минимальный контекст для агента

Перед генерацией или выполнением запроса передайте агенту:

- целевой сценарий и допустимые изменяющие операции;
- базовый URL среды без секретов;
- описание конкретного метода;
- таблицы полей и enum, используемых в запросе;
- правила форматов и ошибок;
- локальные соответствия внешних идентификаторов и ID CARGO.RUN.

Не передавайте агенту всю документацию, если достаточно одного метода и связанных моделей.
